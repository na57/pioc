# 表单业务规则（EOS8 表单设计器，WorkBuddy / Trae 双运行时兼容）

## Overview

在 EOS8 表单设计器中为当前表单添加**业务规则**。
官方描述：当**表单数据初始化**和**表单数据变化**时
将执行业务规则内函数代码，常用于在创建、查看或编辑表单时，
通过设定业务规则改变组件的属性（隐藏、显示、只读、编辑、校验），
也可以计算 formData 数据给定义的变量赋值；
本质上深度监听 formData 数据的变化，然后执行业务规则内函数代码。

流程概览：
确认 IDE 已登录 → AskUserQuestion 确认表单与规则目的 →
表单设置 → 业务设置（业务规则）→ 添加规则
（代码编辑器输入 / 「选择值」 / 「代码助手」辅助）→
保存 → 调试预览验证效果。

**作用域铁律**：仅在当前已打开的表单设计器内操作，
只增改用户确认过的规则，不碰无关表单与其他配置。

## When to use

- 用户要按数据变化联动组件：如某字段为空时禁用子表格。
- 用户要按数据计算赋值：如计算子表格总价赋给标签页标题变量。
- 用户要设置初始化时组件的显示/隐藏/只读/校验逻辑。

## Step 0 — 运行时探测（必须最先执行）

- 工具列表含 `mcp__browser__browsers_list` → **WorkBuddy 模式**。
- 工具列表含 integrated_code_mode 的 `Exec`（`await tools.browser_*`）→ **Trae 模式**。
- 两者都没有 → 提示用户启用对应浏览器扩展，终止流程。

## 参数

- **目标表单**（必填）：当前打开的表单设计器中的表单。
- **规则目的**（必填）：规则要达成的行为描述。
- **涉及字段/组件**（按需）：规则引用的绑定字段名
  （如 OrderSupplier、OrderWarehousingentrydetails）。

缺参数 → `AskUserQuestion` 询问，不要猜。

## Workflow

### Step 1 — 确认 IDE 已打开且已登录

复用 `ynu-lowcode-login` 等产出的 IDE 标签页/viewId；
未登录先执行 `ynu-lowcode-login`。

### Step 2 — 作用域确认（AskUserQuestion，必经）

确认：「将在表单 <表单名> 中添加业务规则：
<规则目的描述，含涉及字段>，是否继续？」

### Step 3 — 打开业务规则编辑界面

1. 点击顶部「表单设置」→ 切换到「业务设置」页签
  （即业务规则）。
2. 重取快照读出现有规则列表（如有），向用户汇报。

### Step 4 — 添加业务规则

1. 点击添加针对当前表单的业务规则。
2. 规则内容在代码编辑器中输入；也可用
   「**选择值**」和「**代码助手**」辅助生成代码。
3. 代码要点（来自官方场景，字段名必须用**绑定字段名**）：
   - 改变组件状态示例（供应商为空时禁用子表格）：
     ```javascript
     if (this.formData.OrderSupplier.id == null) {
       this.Api.setDisabled(true, ['OrderWarehousingentrydetails'])
     } else {
       this.Api.setDisabled(false, ['OrderWarehousingentrydetails'])
     }
     ```
   - 变量赋值示例（子表格总价赋给标题变量）：
     ```javascript
     let total = _.sumBy(this.formData.OrderWarehousingentrydetails, 'totalPrice')
     this.v_title = total == 0 ? "订单详情" : "订单详情(总金额：" + total + ")"
     ```
4. **代码红线（文档明确警告）**：
   - 尽可能避免在业务规则内**改变 formData 内数据**
     （会导致循环调用）；
   - 尽可能避免在业务规则内**请求接口**。
   生成的代码若违反以上两条，停下向用户说明后再定。
5. 保存规则。

### Step 5 — 验证

1. 用「调试预览」触发表单数据初始化/变化场景，
   观察组件状态或变量是否按预期变化。
2. **行动后验证**：以预览中的实际表现为准，
   不以规则保存成功为准。
3. 效果不符 → 原样汇报现象，修改代码需再次确认。

## 不变量

1. **写前必确认**：规则代码内容经 AskUserQuestion 确认后写入。
2. **代码两不写**：不写改 formData、不写请求接口的规则代码。
3. **行动后验证**：以调试预览实际效果为准。
4. **失败即停**：规则不生效两次排查失败即停下汇报。
5. **删除红线**：界面任何「删除」按钮/图标/菜单项严禁点击；
   不删除既有业务规则（如用户要求删除规则，请用户手动）。

## Notes / gotchas

- **循环调用风险**：业务规则深度监听 formData，
  在规则内再改 formData 会循环触发——文档明确警告。
- **接口请求风险**：业务规则内请求接口被文档明确劝阻；
  此类需求考虑扩展逻辑（`ynu-eos8-form-extension-logic`）。
- **字段名用绑定字段名**：代码中引用的是组件绑定的
  字段（如 OrderSupplier），不是组件显示名。
- **「代码助手」优先**：不确定 API 时用「代码助手」
  生成，比手写更符合平台约定。
- **ref 时效性（Trae）**：打开编辑器/保存后快照变化，旧 ref 失效，重新取。
- **CDP 超时（仅 WorkBuddy）**：点击前 focus + sleep 约 2 秒。
- **代码编辑器输入**：长代码逐段输入后回读校验，
  防止自动补全/格式化吞字符。
